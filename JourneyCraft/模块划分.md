# JourneyCraft 系统架构设计

## 技术栈选型

### 1.1 前端技术栈

| 组件    | 技术选型               | 说明      |
| ----- | ------------------ | ------- |
| 框架    | Vue 3.4 + Vite 5.x | 轻量快速    |
| UI 组件 | Element Plus 2.x   | 企业级组件库  |
| 状态管理  | Pinia 2.x          | 轻量状态管理  |
| 地图    | 高德地图 JS API 2.0    | 地图展示与导航 |
| HTTP  | Axios              | 请求库     |
| 路由    | Vue Router 4.x     | 前端路由    |

### 1.2 后端技术栈

| 组件   | 技术选型                  | 说明                  |
| ---- | --------------------- | ------------------- |
| 框架   | Spring Boot 3.2.x     | 主框架                 |
| ORM  | MyBatis-Plus 3.5.x    | 数据库操作               |
| 文档   | Knife4j 4.4.x         | API 文档 (Swagger UI) |
| 对象映射 | MapStruct 1.5.x       | DTO 转换              |
| 工具类  | Hutool 5.8.x          | 工具类库                |
| JSON | Jackson               | JSON 序列化            |
| 认证   | Spring Security + JWT | 用户认证                |


### 1.3 数据存储

| 类型   | 技术选型        | 用途                  |
| ---- | ----------- | ------------------- |
| 关系型  | MySQL 8.0   | 用户、景点、建筑、设施、路径等核心数据 |
| 文档型  | MongoDB 7.0 | 旅游日记、评论、非结构化数据      |

### 2.2 模块职责详细定义

#### user (用户模块)

**划分理由**: 用户是系统的核心实体，所有业务都围绕用户展开。将用户管理独立成模块，实现用户数据的统一管理和维护。

**对应需求**:

- 用户注册/登录
- 个人信息管理
- 偏好设置管理
- 账号信息管理

**核心职责**:

1. 用户账号管理（注册、登录、信息维护）
2. 用户画像管理（偏好设置、出行习惯）
3. 用户状态管理（账号状态、权限）

**依赖关系**:

依赖：无

**边界说明**:

- 仅负责用户账号和基础信息管理
- 不负责认证逻辑（由 auth 模块负责）
- 不负责用户行为记录（由 history 模块负责）

**提供接口**:
| 方法 | 路径 | 说明 |
|------|------|------|
| POST | /api/user/register | 用户注册 |
| POST | /api/user/login | 用户登录 |
| GET | /api/user/info | 获取当前用户信息 |
| PUT | /api/user/info | 更新用户信息 |
| PUT | /api/user/password | 修改密码 |
| PUT | /api/user/preferences | 更新偏好设置 |
| GET | /api/user/preferences | 获取偏好设置 |

#### auth (认证鉴权模块)

**划分理由**: 认证鉴权是系统的安全基石，需要统一管理 JWT 令牌、权限校验等安全逻辑，与其他业务解耦。

**对应需求**:

- 系统安全访问控制
- 用户身份验证

**核心职责**:

1. JWT 令牌生成与验证
2. 请求鉴权拦截
3. 用户身份解析与传递

**数据实体**:

- 无独立实体（使用 User 模块数据）

**依赖关系**:

- 依赖：user 模块（获取用户信息）

**边界说明**:

- 仅负责认证鉴权逻辑
- 不负责用户数据管理

**提供接口**:
| 方法 | 路径 | 说明 |
|------|------|------|

| POST |/api/auth/register |用户注册|

| POST |/api/auth/login |用户登录|
| POST | /api/auth/logout | 用户登出 |
| POST | /api/auth/refresh | 刷新 Token |

#### scenic (景点模块)

**划分理由**: 景点/校园是系统的核心数据实体，包含景区、校园、建筑物、设施等层次化数据，需要独立模块统一管理。

**对应需求**:

- 旅游推荐（景点/学校）
- 景点信息查询
- 旅游服务链接
- 场所查询
- 美食推荐

**核心职责**:

1. 景区/校园数据管理（CRUD）
2. 建筑物数据管理
3. 服务设施数据管理（美食信息维护）
4. 景点搜索与筛选
5. 数据热度维护

**依赖关系**:

- 被依赖：navigationigation、recommend、diary、expense、plan

**边界说明**:

- 仅负责静态数据管理
- 不负责路径规划（由 navigation 模块负责）
- 不负责推荐算法（由 recommend 模块负责）

**提供接口**:
| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /api/scenic/list | 获取景点列表 |
| GET | /api/scenic/search | 搜索景点 |
| GET | /api/scenic/{id} | 获取景点详情 |
| GET | /api/scenic/{id}/buildings | 获取建筑物列表 |
| GET | /api/scenic/{id}/facilities | 获取设施列表 |
| GET | /api/campus/list | 获取校园列表 |
| POST | /api/scenic/{id}/report-crowd | 上报拥挤度 |

#### navigationigation (路线规划/导航模块)

**划分理由**: 导航是系统的核心算法模块，包含路径规划、室内导航等复杂算法，需要独立封装算法逻辑。

**对应需求**:

- 景区内导航
- 多目标路线规划
- 多种路径规划策略
- 室内导航
- 实时拥挤度感知与反向游览建议
- AR 式打卡引导

**核心职责**:

1. 单目标路径规划（Dijkstra/A*算法）
2. 多目标路线规划（TSP 变种算法）
3. 室内导航（楼层间路径）
4. 实时拥挤度计算
5. ~~反向游览建议生成~~
6. 拍照点推荐
7. 路网数据管理

**依赖关系**:

- 依赖：scenic 模块（获取路网数据）
- 被依赖：group 模块（生成协同方案）

**边界说明**:

- 仅负责路径计算和导航逻辑
- 不负责景点数据管理
- 不负责用户历史记录（由 history 模块负责）

**提供接口**:
| 方法 | 路径 | 说明 |
|------|------|------|
| POST | /api/navigation/route | 单目标路径规划 |
| POST | /api/navigation/multi-route | 多目标路线规划 |
| GET | /api/navigation/facilities/nearby | 获取附近设施 |
| POST | /api/navigation/indoor/route | 室内导航 |
| GET | /api/navigation/congestion/{scenicId} | 获取实时拥挤度 |
| GET | /api/navigation/photo-spots/{scenicId} | 获取拍照点推荐 |
| GET | /api/navigation/alternative-route | 获取反向游览建议 |

#### recommend (推荐算法模块)

**划分理由**: 推荐是系统的智能核心，包含热度计算、协同过滤、内容推荐等多种算法，需要独立封装。

**对应需求**:

- 景点推荐（按热度、评价、兴趣）
- 美食推荐
- 旅游日记推荐

**核心职责**:

1. 景点推荐
2. 协同过滤推荐
3. 美食推荐（按距离、评分、菜系）
4. 日记推荐
5. 各种分数的维护

**数据实体**:

- 无独立实体（使用其他模块数据 + 缓存）

**依赖关系**:

- 依赖：scenic、diary、user 模块
- 被依赖：plan

**边界说明**:

- 仅负责推荐算法和排序
- 不负责数据存储
- 不负责用户行为收集（由 history 模块负责）

**提供接口**:
| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /api/recommend/scenic | 热门景点推荐 |
| GET | /api/recommend/personalized | 个性化景点推荐 |
| GET | /api/recommend/foods | 美食推荐 |
| GET | /api/recommend/diaries | 日记推荐 |

#### group (多人同行规划模块)

**划分理由**: 多人协同规划，需要管理旅游小组和偏好信息收集并生成旅游方案，逻辑相对独立。

**对应需求**:

- 同行人协同规划
- 多人最优方案生成

**核心职责**:

1. 协同方案生成（旅游小组管理、组员偏好收集、最终方案生成）

**依赖关系**:

- 依赖：user、scenic、navigationigation 、recommend模块
- 被依赖：无

**边界说明**:

- 仅负责小组管理和旅游方案综合
- 不负责具体路径规划（调用 navigation 模块）
- 不负责具体景点、美食的推荐（调用recommend模块）

**提供接口**:
| 方法 | 路径 | 说明 |
|------|------|------|
| POST | /api/group/create | 创建小组 |
| GET | /api/group/list | 获取小组列表 |
| GET | /api/group/{id} | 获取小组详情 |
| POST | /api/group/{id}/join | 加入小组 |
| POST | /api/group/{id}/preference | 提交偏好 |
| POST | /api/group/{id}/generate-plan | 生成协同方案 |
| GET | /api/group/{id}/expense | 获取小组账单 |

#### diary (日记模块)

**划分理由**: 日记是旅游后场景的核心功能，使用 MongoDB 存储非结构化数据（文字、图片、视频），需要独立管理。

**对应需求**:

- 旅游日记撰写与发布
- 旅游日记浏览、评分与推荐
- 旅游日记交流与检索
- 旅游日记压缩与内容生成
- 自动生成旅游日记

**核心职责**:

1. 日记 CRUD
2. 日记媒体文件管理（图片、视频）
3. 日记搜索与检索
4. 日记互动（点赞、评论）
5. 自动日记生成
6. 日记热度统计

**依赖关系**:

- 依赖：user、scenic、file 模块
- 被依赖：recommend 模块

**边界说明**:

- 仅负责日记内容管理
- 不负责文件存储（由 file 模块负责）
- 不负责推荐算法（由 recommend 模块负责）

**提供接口**:
| 方法 | 路径 | 说明 |
|------|------|------|
| POST | /api/diary | 创建日记 |
| GET | /api/diary/list | 获取日记列表 |
| GET | /api/diary/{id} | 获取日记详情 |
| PUT | /api/diary/{id} | 更新日记 |
| DELETE | /api/diary/{id} | 删除日记 |
| POST | /api/diary/{id}/like | 点赞日记 |
| POST | /api/diary/{id}/comment | 添加评论 |
| GET | /api/diary/{id}/comments | 获取评论列表 |
| POST | /api/diary/auto-generate | 自动生成日记 |
