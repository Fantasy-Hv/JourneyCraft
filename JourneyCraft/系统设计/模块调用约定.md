# 模块之间调用规范

## 1. 基本调用方式

假设日志模块需要调用文件模块存储文件。
- 文件模块（file）需要在 `api` 包下创建一个 Java 接口，例如 `FileService`
- 然后在本模块 `service/impl` 中提供实现类，并加上 `@Service`
- 调用方在需要使用该能力的类中注入接口类型成员变量即可

具体可参考 `file` 模块的 `api` 包和 `service` 包。

## 2. zhe / liu 合并阶段接口冲突处理约定

### 2.1 拥挤度能力归属

| 能力 | 最终归属模块 | 对外接口 | 说明 |
|------|--------------|----------|------|
| 拥挤度上报 | scenic | `POST /api/scenic/{id}/report-crowd` | 景点模块负责接收上报并落库 |
| 拥挤度聚合查询 | navigation | `GET /api/navigation/congestion/{scenicId}` | 导航模块负责聚合并返回前端展示结果 |

### 2.2 拥挤度表归属

| 项目 | 最终方案 |
|------|----------|
| 最终保留表 | `t_crowd_level` |
| 负责模块 | scenic |
| 用途 | 保存节点级拥挤度原始记录 |
| navigation 是否单独建表 | 否 |

### 2.3 最终字段定义

| 字段名 | 类型 | 说明 |
|--------|------|------|
| `id` | `BIGINT` | 主键 |
| `scenic_area_id` | `BIGINT` | 景区 ID |
| `node_id` | `BIGINT` | 节点 ID |
| `level` | `TINYINT` | 拥挤等级，`0/1/2/3` |
| `crowd_count` | `INT` | 人数，可空 |
| `capacity` | `INT` | 容量，可空 |
| `predicted_at` | `DATETIME` | 预测时间，可空 |
| `recorded_at` | `DATETIME` | 记录时间 |
| `source` | `TINYINT` | 数据来源，当前约定 `1=用户上报 2=系统采集` |
| `created_at` | `DATETIME` | 创建时间 |
| `updated_at` | `DATETIME` | 更新时间 |
| `is_deleted` | `TINYINT` | 逻辑删除 |

### 2.4 合并处理原则

| 冲突项 | 处理规则 |
|--------|----------|
| scenic 与 navigation 都定义拥挤度实体 | 以 scenic 的 `t_crowd_level` 为最终落库表 |
| navigation 的拥挤度接口 | 保留查询聚合接口，不负责原始记录落库 |
| navigation 独立拥挤度表/脚本 | 视为独立开发阶段桩实现，后续联调时逐步移除 |

## 3. user 模块分层约定

模块内部业务接口放在 `service` 包，供本模块的 `controller` 调用。
模块对外接口放在 `api` 包，供其他模块跨模块调用。

实现类可以同时实现 `service` 和 `api` 两个接口，作为联调阶段的最小改动方案。

例如用户模块：
- `user/service/UserService.java`：用户模块内部业务接口
- `user/api/UserApi.java`：跨模块对外接口
- `user/service/impl/UserServiceImpl.java`：同时实现上述两个接口

调用方在需要用到对外接口时，直接注入 `api` 包下的接口类型即可。
